Quickstart

Copy, paste, wait.

You need

  • A Hetzner Cloud project and an API token with Read & Write access, made at console.hetzner.com
  • The hcloud CLI, logged in: brew install hcloud, then hcloud context create fc-node
  • An SSH key in ~/.ssh (ssh-keygen -t ed25519 if you don't have one)
  • Node.js 22.18 or newer, and git
  • To post: a Farcaster account that already has storage. Use a test account; see seed phrases

  1. Create the server

    A cx43 (8 vCPU, 16 GB RAM) with a 1000 GB volume, about $0.16/hour. If cx43 is sold out it tries other locations, then cpx41 (~$0.20/hour), and says which it got. It prints the next two commands with your server's IP filled in.

    curl -fsSL https://raw.githubusercontent.com/eucalyptus-viminalis/create-fc/main/provision/hetzner.sh | bash

  2. Set up the node

    Give the server a minute to boot. Setup runs in the background, so you can close the terminal. Check on it with ssh root@<ip> fc-node status.

    ssh root@<ip> 'curl -fsSL https://raw.githubusercontent.com/eucalyptus-viminalis/create-fc/main/node/setup.sh | bash'

  3. Install the client

    When fc-node status says "in sync", run this on your own computer. Then clearcast ui opens the client in your browser, or try clearcast feed dwr in the terminal.

    curl -fsSL https://raw.githubusercontent.com/eucalyptus-viminalis/create-fc/main/client/install.sh | bash -s -- http://<ip>:3381

Done for now?

Delete the server so it stops billing. It asks before deleting anything.

curl -fsSL https://raw.githubusercontent.com/eucalyptus-viminalis/create-fc/main/provision/hetzner-delete.sh | bash

Already have a Linux box with 16 GB of RAM and ~700 GB free? Skip step 0 and run step 1's curl … | bash on it as root. There is no npm package: npm create clearcast runs an unrelated package someone else published in 2022.

Tutorial

What each command does, and why.

The quickstart works without reading any of this. Read it when you want to know what's running on your server, what you just signed, or what to do when something breaks. Every output and timing here is from a real run on 18–19 October 2026.

Before you start: Hetzner

Command 0 uses Hetzner Cloud because it bills by the hour and has a clean CLI. Hetzner has no API for creating projects or tokens, so this part happens in the browser:

  1. Sign up at console.hetzner.com. New accounts may need ID or payment verification before they can create servers, which can take a while. Do this first.
  2. Create a project, then Security → API tokens → Generate API token with Read & Write access. Hetzner shows it once.
  3. Run hcloud context create fc-node and paste the token. It's saved in plain text in ~/.config/hcloud/cli.toml. A project used only for this keeps the token's reach small.

New accounts can only have 1024 GB of volumes in total, and Hetzner won't raise that until the account is older: the Limits page says "Your account is too new to request a limit increase." The official Snapchain installer needs about 2 TB, so we load the database differently (see command 1) and fit in 1000 GB.

Command 0: the server

provision/hetzner.sh creates four things, each named so a re-run finds and reuses it: an SSH key, a firewall, a volume, and the server. The volume comes first, so it's attached when the server first boots and formats it at /srv/snapchain.

The firewall opens exactly what a read node needs:

PortProtocolFor
3381TCPHTTP API. Your client talks to this.
3382UDPGossip with other nodes (libp2p over QUIC). A TCP-only rule leaves the node unable to peer.
3383TCPgRPC API, the same data as 3381 for other tools
22TCPSSH
3000TCPClosed. The node ships Grafana with the login admin / admin.

Server types sell out. When Hetzner has no cx43 free in a location, it answers error during placement (resource_unavailable) and creates nothing. We watched cx43 disappear from all three EU locations within a minute, then come back in Nuremberg five minutes later. The script handles it: cx43 in fsn1, nbg1 and hel1, then cpx41 (the same 8 vCPU and 16 GB at about twice the server price) in the same order. It creates the server first and the volume after, in the server's location, because a volume can't move between locations. Pin your choice with TYPE=cx43 or LOCATION=hel1.

If the volume step fails with volumes size limit exceeded (resource_limit_exceeded), your account's volume cap is lower than VOLUME_GB. Check Limits in the console. Other sizes and locations can be set with environment variables: … | TYPE=ccx23 LOCATION=nbg1 bash.

Command 1: the read node

Snapchain is the network that stores Farcaster's messages: every cast, like, follow and profile change. Its official installer, snapchain.sh, runs the node in Docker. node/setup.sh wraps it, starts it as a systemd job so you can disconnect, and changes one thing: how the database gets loaded.

Loading the snapshot

A new node doesn't replay Farcaster from the beginning. It downloads a daily snapshot of each shard (about 397 GB compressed, in ~70 MB pieces) and then fetches the blocks made since. The node's own loader keeps every downloaded piece and an uncompressed copy of each shard until all three are unpacked. We estimate that peaks around 1.5 TB, which is why the docs ask for 2 TB.

fc-load-snapshot streams instead: download a piece, unzip it straight into the database, delete it, repeat. The node only downloads a snapshot when its database folder is empty, so afterwards it boots straight into catching up.

Catching up

Our snapshot was 22 hours old by the time it finished loading. The node fetched the missing blocks at about 5 per second per shard and closed the gap by about 4 seconds every second, so it was in sync roughly 5½ hours later. On a second, timed run the snapshot was 19 hours old and the node caught up in 4 hours 25 minutes: 6 h 20 min from command 0 to in sync. The CPU sat 94% idle: the limit is fetching blocks from peers one after another, not the server.

on the server
$ clearcast status
node http://2.28.135.100:3381 · snapchain 0.14.3
  shard 0  height 48242370  47661s behind
  shard 1  height 48938063  26552s behind
  shard 2  height 48754698  45879s behind
catching up: 13.2h behind. Reads work now, but recent casts may be missing.

That's two hours into catching up. Five hours later every shard read 0–3 s behind. On the server, fc-node status reports the same numbers, and during setup it shows the snapshot's progress instead.

"Behind" is blockDelay from /v1/info: how many seconds each shard's newest block trails the clock. A synced node stays in single digits. In the same response, mempoolSize: 4294967295 is normal on a read node. It means "not reported", not an overflow.

Two things look alarming and aren't. Failed to dial peer … HandshakeTimedOut for a couple of the bootstrap addresses, and a steady trickle of InsufficientPeers ("read-node-peers"). Our node logged both all day and synced fine.

Why not the official one-liner? snapchain-bootstrap.sh reads its prompts from /dev/tty, which doesn't exist over ssh host 'curl … | bash' or in a systemd job. setup.sh answers both prompts in .env ahead of time and runs snapchain.sh upgrade directly.

Command 2: the client

install.sh clones this repo into ~/.fc-client/app, installs three dependencies (@farcaster/core, viem, @scure/bip39), saves your node's address in ~/.fc-client/config.json, and puts clearcast in ~/.local/bin. Node.js runs the TypeScript directly, with no build step.

Reading

Every read is a plain GET to your node, so you can repeat any of them with curl:

your computer
$ clearcast casts pinkmink -n 1
@pinkmink · 2m · via @pinkmink  0x085bf8a4
hello from my own snapchain read node 👋

$ curl "http://<ip>:3381/v1/castsByFid?fid=3355372&reverse=true&pageSize=1"

Snapchain has no "home feed" endpoint. A feed is something a client builds. Ours is the simplest version: ask the node who you follow, fetch the latest casts from each, and merge them by time. That's one request per account you follow. For an account following 1,041 people, the feed took 13.5 seconds from Sydney to our node in Germany, while the same 1,041 requests made on the server itself took 1.7 seconds. Running the client close to the node pays off.

One oddity: a few old casts carry timestamps decades in the future (we found one dated 2061). They would sit at the top of any time-sorted feed forever, so clearcast feed skips anything more than 10 minutes ahead.

A username

clearcast username alice claims a name and sets it. It's the one step that uses a service other than your node: the fname server at fnames.farcaster.xyz, run by Farcaster, free, no key. Your custody key signs the claim, the fname server countersigns, the proof reaches the network and then your node, and only then will the node accept a message setting your username.

Filtering by the app that posted

Every cast is signed by an app key, and every app key records which app asked for it. So clearcast labels each cast with its app, and filters on it:

your computer
$ clearcast apps dwr
   1 key   @warpcast (fid 9152)
   1 key   @baseapp.base.eth (fid 309857)
   1 key   @neynar (fid 6131)

$ clearcast feed me --not-app warpcast
$ clearcast feed me --app fireflyapp --app 9152

In one account's feed of 16,416 recent casts, 89% came through the Farcaster app (fid 9152, still called @warpcast). Excluding it is a quick way to see what everything else looks like.

Concepts

The pieces you just used.

FID
A Farcaster account is a number, its FID, registered on OP Mainnet (Optimism). Usernames, keys and storage all hang off it. Our test account is 3355372.
Custody address
The Ethereum address that owns the FID, derived from the seed phrase. Most wallets use the first address, m/44'/60'/0'/0/0; clearcast login checks that one first, then the next nine. It can transfer the account and add or remove keys. It never needs to sign a cast.
App keys (signers)
Ed25519 keys that sign everyday messages for one app. The custody key authorizes each one, naming the app that asked (its requestFid). One account can have many: Farcaster's app, Firefly, this client.
Gasless app keys
App keys used to be registered with an Optimism transaction. Now a KEY_ADD message does it: no transaction, no gas, about a second. Each key lists the message types it may sign (its scopes) and expires after 30–90 days unused.
Snapchain messages
Casts, reactions, follows and profile fields are signed protobuf messages. Timestamps count seconds from 1 January 2021, not 1970. A message's ID is a 20-byte BLAKE3 hash, the 0x085bf8a4… you see in clearcast.
Shards
Snapchain splits users across shards 1 and 2 by a hash of the FID. Shard 0 orders the other two and holds things every shard needs, like app keys. Each shard is its own chain, so their heights differ.
Read nodes vs validators
Validators propose and vote on blocks; there's a fixed set of them. A read node, like yours, fetches the decided blocks, checks their signatures, and serves the API. Anyone can run one.
Mempool and submission
Your read node accepts writes: it checks the message, gossips it to the validators, and keeps nothing. "Accepted" means "valid and relayed", not "in a block". That's why clearcast reads every write back. If gossip drops it, send it again.
Storage rent
An account needs rented storage units to post, paid on Optimism. One unit comes with registration (about $0.20 when we checked). When a store fills up, the oldest messages are pruned. clearcast login checks there's at least one unit.
fnames
Usernames like @dwr come from the fname server, which signs a proof that the network stores. ENS names (.eth) work too.

Seed phrases

Treat it like rm -rf.

A seed phrase is the master key to an account. Whoever has it can post as you, move your FID to themselves, and take any funds at the custody address. Like rm -rf, it's a normal tool that's unforgiving when used carelessly.

Use a test account

Not your main one. client/scripts/new-test-account.ts makes a fresh account for about $0.20 of ETH on Optimism, and shows its phrase once.

Read before you paste

Only give a seed phrase to software from developers you trust, after reading what it does with it. For this client that's client/src/keys.ts: in memory, one signature, never written or sent.

Prefer delegated signing

The better pattern: the app shows a request, your wallet approves the key, and the phrase never leaves the wallet. Paste a phrase only when no such flow exists, as here.

Not through an AI's shell

We learned this one live: run through a coding assistant's shell, the account script's output, phrase included, landed in the chat transcript. Run phrase commands in your own terminal.

When it breaks

Errors we actually hit.

volumes size limit exceeded

Your account's total volume cap is below the requested size. New accounts get 1024 GB and can't ask for more yet. Keep VOLUME_GB at 1000 or less.

error during placement (resource_unavailable)

That server type is sold out in that location. Command 0 moves on by itself, ending with cpx41. If you pinned TYPE or LOCATION, try another, or wait a few minutes.

clearcast prints its help instead of running

A pasted command can carry invisible characters. clearcast now says unknown command "username​" (it contains hidden characters…). Retype the command.

clearcast login spends minutes on "checking indexes 1-9"

The phrase's first address owns no account, and your node scans all 3.3 million registrations before answering "not found", 30–40 s each time. Check it's the right phrase.

"not visible on your node yet" after a write

Read nodes relay and forget. If the gossip was lost, the message is gone: run the command again. We haven't lost one yet.

fc-node status: "isn't answering and setup isn't running"

Setup stopped partway. Run command 1 again: finished shards are skipped and a partial one is redone.
